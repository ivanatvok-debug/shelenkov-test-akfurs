# Входы и логика Q1–Q4

Область: модули Python CLI. Реализованы частные `crm.py` для Q1, `bank.py` для Q2 и `pricing.py` для Q3; остальные предметные модули запланированы. План модулей — в [архитектуре](../../docs/ARCHITECTURE.md); формат полного выхода — в [контракте](../../contracts/AGENTS.md).

## Загрузка и общий расчёт

- Читай четыре операционных входа только из переданного каталога. Проверяй наличие, формат, скрытые листы и полноту; не теряй строки молча.
- За один запуск вычисляй Q1–Q4 из сырья. Не используй сохранённые ответы, списки ID, фиксированное число строк/чатов или имена клиентов как расчётную логику.
- Для денег применяй точную десятичную арифметику; промежуточное округление не должно менять сравнение с порогом.
- При отсутствии входа, неподдержанном формате, неоднозначности, меняющей ответ, или сбое Q4 заверши запуск явной ошибкой. Не подменяй невычисленный ответ нулём, `null` или пустым массивом.
- Кэш, если понадобится, привязывай к содержимому входа и версии правил/анализатора; одного ID чата недостаточно.

## Q1 — CRM

- Нормализуй `A-00075`, кириллическую `А-75`, `a-75`, `A75` к числовому номеру `75`.
- Ключ строки — `(order_id, line_no)`. Счётчики Q1 — количества различных ключей и номеров заказов, без фильтра по статусу. Для канонической CRM выбирай максимальное значение `Выгружено`; конфликт разных payload с одинаковым максимумом удерживает готовность CRM для Q2/Q3, но не меняет счётчики при достоверных ключах. Не разрешай конфликт порядком чтения; идентичные последние версии сохраняют все локаторы.
- Приводи статусы к «Оплачен», «Отменён», «Возврат», «В работе»; всё вне первых трёх относится к «В работе».
- Сохраняй локальную связь выбранных значений с источником для сверки Q1 и зависимых Q2/Q3.

## Q2 — банк

- Учитывай только поступления. Связывай их с существующим заказом по номеру в контексте назначения платежа.
- Сумма, плательщик, дата или телефон сами по себе не доказывают связь. Не удаляй операции по совпадающим суммам.
- Неоднозначное назначение с несколькими заказами обрабатывай по принятому на R0 правилу.
- Для Q2a выделяй оплаченные заказы без единого поступления; это не доказательство задолженности. Для Q2b считай количество и сумму неопознанных поступлений.

## Q3 — цены

- Проверяй все выбранные строки, кроме «Отменён». Учитывай переименования артикулов и канонические имена менеджеров из справочника.
- Бери исторический минимум на дату создания заказа со скрытого листа `Прайс_история`, а не на дату экспорта.
- Процентная скидка применяется к `цена × количество`; фиксированная скидка вычитается один раз на строку.
- Цена за единицу после скидки: `(цена × количество − скидка_строки) / количество`. Равенство минимуму не является нарушением.
- Сверяй общее число нарушений с разбивкой по менеджерам и локальными построчными основаниями.

## Q4 — переписки

- Предусмотри AI-анализ и проверку его результата, как требует ТЗ. Механизм и возможность повторного анализа нового чата проверяются на R0; сейчас они не выбраны.
- Различай цену менеджера, сумму клиента, предоплату, скидку, конкретное приглашение, отрицание приглашения и отсутствие события. Учитывай цены прописью.
- Сохраняй локальные основания событий: ID чата, порядковый номер сообщения, роль, точную цитату или проверяемый фрагмент, тип события. Проверяй их наличие в источнике и порядок событий.
- Согласуй на R0 сообщения с несколькими событиями. Отсутствие цены и неуспешный анализ — разные состояния.
- Если используется модель, фиксируй модель/версию, запрос, правила, среду, доступ и повторный запуск. Сбой доступа не должен превращаться в пустой Q4.
- Проверка цитат и ролей не заменяет смысловую проверку; согласие двух AI не заменяет обращение к исходным сообщениям. Повторяемость модели не означает абсолютной детерминированности.
