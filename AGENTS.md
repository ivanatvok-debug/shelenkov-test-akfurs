# Инструкции для AI-агента

Репозиторий `ivanatvok-debug/shelenkov-test-akfurs` содержит решение тестового задания AK Furs. Один Python CLI рассчитывает Q1–Q4. Q5 готовится отдельно.

## Требования и границы работы

- Перед изменениями прочитай задачу и применимые инструкции. Проверь состояние Git и затрагиваемые файлы. Оцени риски.
- Выполняй только разрешённую работу. Наличие кода или инструментов не разрешает запуск на реальных данных.
- Сверяй требования с исходным ТЗ и `answers_template.json` в `inbox/`. Не заменяй их проектными документами или решениями владельца. При противоречии запиши его в журнал и запроси уточнение.
- Сохраняй структуру одного CLI. Не добавляй CRM, веб-интерфейс, базу данных, сервисы, Docker, CI или универсальный фреймворк без отдельного основания и разрешения.
- До выполнения согласуй сетевые действия, установку и изменение зависимостей, операции с секретами, удаление, действия в рабочей системе и внешнюю публикацию. Не меняй настройки GitHub без разрешения.
- Не зашивай ответы текущего набора данных в код. Не выдумывай тесты, ошибки AI, экспорт сессии, историю коммитов или решения владельца.

## Исходные данные и результаты

- Не изменяй файлы в `inbox/` и `data/`.
- Сохраняй локальные результаты и основания расчётов в исключённом из Git каталоге `private/`.
- Не включай в Git исходные данные, переписки, результаты Q1–Q5, диагностику с данными и неочищенные AI-экспорты.
- Не выводи секреты и не добавляй их в Git.
- Перед каждым `git add` проверь отслеживаемые файлы и содержимое индекса. Добавляй файлы по точному списку путей.
- Не полагайся на `.gitignore` для уже отслеживаемых файлов. При обнаружении закрытых данных в истории Git останови публикацию. Новый коммит с удалением файла не удаляет его из истории.

## Работа с таблицами

Для разрешённых операций с табличными данными используй локальные Skills:

- `akfurs-xlsx`: чтение и создание нового экспорта.
- `akfurs-data-quality`: проверка данных до нормализации и объединения таблиц.
- `akfurs-reconciliation`: сверка по явным ключам и заданным допускам.
- `akfurs-validation`: независимая проверка по исходным записям.

Общая команда инструментов:

```bash
.venv/bin/python -m tools.data_processing
```

Инструкция: `docs/data_skills/USAGE.md`.

Исходники только читай. Новые файлы сохраняй в `private/data_skills/`. Не перезаписывай существующие результаты.

## Q4: адаптеры и запуск

Сохраняй общую предметную схему Q4. Модуль `q4_adapters.py` запускает Codex или Claude и разбирает ответ CLI. Функция `chats.evaluate()` проверяет извлечённые события.

Адаптер Claude проверен локальными протокольными тестами. Живой запуск через Claude не проверен.

Перед запуском модели согласуй доступ, передачу данных, бюджет вызовов и возможные расходы. CLI может выполнять внутренние сетевые попытки. Их полное число не контролируется счётчиком процессов. Не обещай отсутствие повторов на основании настройки retries=0.

Размещай журнал вызовов и основания расчёта вне входного каталога.

## Проверки

Запускай тесты в подготовленном окружении:

```bash
PYTHONDONTWRITEBYTECODE=1 python -m unittest discover -s tests -p 'test_*.py' -v
```

Эти тесты не обращаются к моделям. Проверки адаптеров находятся в `tests/test_q4_adapters.py` и используют локальные дочерние процессы.

- Проверяй затронутую область. Расширяй проверки, если изменение влияет на другие результаты.
- Используй `docs/REQUIREMENTS_MATRIX.md` для связи требований с кодом и проверками. Не создавай дублирующую матрицу.
- При расхождении отчёта с исходными данными проверяй исходные записи и требования.
- Не называй AI-основания человеческой разметкой. Совпадение итоговых счётчиков не заменяет независимую проверку.
- Различай самопроверку, независимую проверку и приёмку владельцем. Отдельно указывай локальные тесты и живые вызовы модели.
- Не выдавай неполный результат за готовый. Блокировка одного этапа не запрещает независимую работу в разрешённых границах.

Используй статусы `NOT_CHECKED`, `PASS`, `FAIL` и `HOLD` с указанием области и основания. Для `HOLD` укажи причину блокировки.

## Стиль документации

Используй адаптированные для русского текста принципы [ASD-STE100](https://www.asd-ste100.org/):

- Пиши короткими предложениями.
- Используй один термин для одного понятия.
- Указывай исполнителя действия. Предпочитай активный залог.
- Записывай одно действие в одном шаге инструкции.
- Отделяй факты от допущений, а выполненные действия от предложений.
- Сохраняй точные имена файлов, команд, параметров и полей.
- Убирай повторы и редакторские комментарии. Сохраняй ограничения, которые влияют на запуск или оценку результата.

## Отчёт о работе

Передавай результат кратко:

1. Что изменено и в каких файлах.
2. Какие проверки выполнены и что они подтвердили.
3. Что не проверено и почему.
4. Какие допущения и риски остались.
5. Какой следующий шаг разрешён.

Не называй подготовленный результат отправленным. Не называй проверенный результат принятым владельцем без подтверждения.
